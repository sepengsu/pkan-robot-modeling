# A0509 simulated residual dynamics: structured spline/KAN study

This directory is an **offline** experiment. Labels are MuJoCo `qfrc_inverse`
generalized forces, not measured A0509 motor torque. No ROS 2 launch file or
robot-control path is used or modified.

## Physical definitions and controlled experiments

The signed generalized torque convention is copied from `RBDModel`: joint
order `joint_1`…`joint_6`, `q` radians, `dq` rad/s, `ddq` rad/s², and output Nm.
The pipeline re-evaluated every selected state with the archived scene and
found a maximum discrepancy of **1.2545e-5 Nm** against saved
`qfrc_inverse`. This checks sign, coordinates, assets, and parameter matching.
The scene XML mass/inertia for every body plus gravity, damping, armature, and
frictionloss are recorded in `prepared_d/manifest.json`.

| Setting | Label | RBD treatment | Interpretation |
|---|---|---|---|
| A, consistency | Original saved-scene `qfrc_inverse` | M1 uses that exact scene and physics | Residual is zero by construction. This is a simulator reconstruction check, not independent prediction. |
| B, unmodeled friction | Recompute `mj_inverse` after setting each joint's MuJoCo `dof_frictionloss` to `[0.40, 0.35, 0.25, 0.15, 0.12, 0.08]` Nm | M1 retains the original zero-friction scene | Difference is an actual MuJoCo passive-friction effect. Every other scene parameter is held fixed. |

M0 is the archived **nominal** RBD, where tool and payload masses and inertias
were scaled to 80% while arm inertials and centers of mass remained unchanged.
That 80% mismatch is synthetic. M1 is sometimes called “calibrated RBD” in
the model list, but here it means the **exact simulator scene**, not a
parameter fit to physical hardware. The old scene and nominal model use the
same gravity, damping, armature, and force convention. Dataset quality gates
exclude cross-robot contact samples, and this experiment does not add external
forces or contact. MuJoCo `frictionloss` is a velocity/constraint effect and
can depend on acceleration close to zero velocity; a smooth velocity spline
need not fit it exactly.

## Models and branch identifiability

All learned outputs are six-dimensional *residual* torque in Nm. They are
added to M1. All branches use the same rows and training-only normalization.
Condition features are present in the archive for stratification but are
deliberately excluded from this first shared-model study.

| ID | Residual input | Structure | Trainable parameters (5-grid) |
|---|---|---|---:|
| M0 | `q,dq,ddq,condition` | Archived nominal RBD | 0 |
| M1 | `q,dq,ddq,condition` | Exact-scene MuJoCo RBD | 0 |
| M2 | `q,dq` (12) | MLP `[12,25,25,6]` | 1,131 |
| M3 | `dq_i` (one per joint) | Six independent cubic B-spline functions | 54 |
| M4 | `q,dq` (12) | Two-layer edge-spline KAN `[12,8,6]` | 1,166 |
| M5 | `dq_i` and `q,dq` | Frozen trained M3 + M4-shaped coupled branch trained on the remaining residual | 1,220 total |

Spline degree is 3. The default number of grid intervals is 5, with 3 and 8
in ablations. Knot positions and learned coefficients are exported for every
seed. M3 is a 1D spline additive baseline, not a multilayer KAN. M5's staged
training freezes M3 before fitting the coupled branch; this prevents both
branches from jointly claiming the same residual without a convention. It
does not prove a unique physical decomposition.

Adam, learning rate 1e-3, batch size 256, three seeds, validation early
stopping, and optional coefficient second-difference and correction-size
penalties are configured in `config.json`. Epoch history includes training and
validation losses, per-joint validation RMSE, total RMSE, and elapsed time.
The MLP and coupled KAN receive the same `q,dq` input, target, row split,
epoch limit, optimizer, and tuning budget; their parameter counts differ by
3.1%. This is a fixed-budget comparison, not an exhaustive architecture
search.

## Reproduce

Run in `F:\robot_modeling`. The commands read the dataset and MuJoCo XMLs
**directly from D:**; they do not require a copy under `F:\robot_modeling\data`.
The checked environment is the source project's `model/.venv` (Python 3.12,
exact versions in `requirements.txt`). Each command refuses to overwrite an
existing output; pass a fresh path when rerunning.

```powershell
$py = 'D:\Code\sdml-doosan-robot\model\.venv\Scripts\python.exe'
& $py -m src.model prepare
& $py -m src.model train
& $py -m src.model evaluate
& $py -m unittest discover -s src/model/tests -v
```

The `prepare` command reads the archived NPZ and original condition XMLs on
D: and records a detailed physics manifest. Training and evaluation thereafter
use only `result/structured_kan/prepared_d`; no bulk data copy is needed. The
outputs are `models_d` and `evaluation_d` under `result/structured_kan/`,
which is excluded from Git. The optional 36-run ablation is invoked with
`& $py -m src.model ablate`.

Current execution status: D-drive preparation, M2–M5 training (three seeds),
held-out evaluation, figures, and five unit tests are complete. The 36-run
grid/smoothness/acceleration ablation is implemented but has not completed;
no ablation conclusion is reported here. M6 remains deferred.

## Interpretation and questions

1. **Residual after calibrated RBD?** In A, no: exact-scene RBD reproduces
   saved labels to 1.2545e-5 Nm. In B, yes: the omitted friction causes
   0.2066 Nm test RMSE. This is simulated passive friction, not evidence of a
   real A0509 unmodeled drive effect.
2. **Is a jointwise spline enough?** For this B setting, largely yes. Its
   0.02448 Nm test RMSE explains most of the friction residual. Near zero
   velocity error remains; see Fig. 2, Fig. 6, and `spline_analysis.json`.
3. **Does coupling help?** M4 is worse than M3, and M5 slightly worsens the
   held-out score relative to M3. The added friction is primarily per joint,
   so this result is physically consistent. It does not settle cases with
   genuinely coupled unmodeled dynamics.
4. **Does KAN beat an equally sized MLP?** In this fixed-budget comparison,
   M4 beats M2, but the MLP has large seed variation. Three seeds and one
   shared hyperparameter setting do not establish a statistically robust KAN
   advantage. The 54-parameter M3 is the clearest model for this target.
5. **How do gripper/payload changes affect the spline?** The shared M3 uses
   the same six functions for every condition. Its similar condition scores
   reflect that the same frictionloss was added across conditions. This study
   has not measured condition-specific function changes.
6. **What warrants KAN?** These results support a simple velocity spline for
   added joint friction. They do **not** show a need for a coupled KAN over
   the jointwise baseline, nor any real-world performance gain.

M6 adaptive KAN and Fig. 9 are deliberately deferred until shared-model
results justify them. A future study could first introduce a verified
condition-dependent discrepancy, then compare a small gated adapter to
shared-only models under held-out conditions. Continual learning should only
follow that task-adaptation test. No 1.5 kg data or measured motor torque is
available for those claims.

## Scope and limitations

The tested residual is friction introduced by changing MuJoCo `frictionloss`,
not a discovered property of the real robot. Nominal RBD error is mainly a
deliberate tool/payload inertia mismatch and must not be presented as
nonlinear friction. The exact-scene M1 result is tautological. The saved
simulation tool inertials are assumptions, so no physically calibrated
hardware RBD comparison is possible from these files. Model tuning and
split choices were made before inspecting test results; any further tuning
should retain T13/T14/T16 as a final holdout.
